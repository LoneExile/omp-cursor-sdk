# AGENTS.md

## Purpose

This repository is an omp (oh-my-pi) plugin, ported from the Pi extension fitchmultz/pi-cursor-sdk, that registers Cursor SDK-backed models under the `cursor-sdk` provider (`CURSOR_PROVIDER` in `src/cursor-model.ts`; omp 18.x owns the built-in `cursor` provider). The host baseline is omp 18.3.4 with `@oh-my-pi/*` 18.3.4 and `@cursor/sdk` 1.0.40. Agent work is successful when changes preserve omp-native model/thinking/session behavior, keep Cursor API keys out of repo state and logs, and pass the local validation commands below.

## Repository map

- `src/index.ts` registers the pi extension, provider, fallback warnings, Cursor runtime controls, native replay wrappers, question tool, and pi tool bridge hooks.
- `src/model-discovery.ts` discovers Cursor models, builds pi model metadata, stores per-model metadata, and defines fallback models. It keeps each base model's catalog variants whole, `ModelVariant.isMaxMode` included. `isCursorSelectionMaxModeOnly` is the Max Mode only rule, the one `@cursor/sdk` 1.0.40's local catalog resolver applies: the selection has params, at least one catalog variant matches them, and every matching variant is `isMaxMode`. A model with no catalog variants is never Max Mode only. `getCursorNonMaxModeAlternatives` lists the registered ids of the same model that do not need Max Mode. `src/model-list-cache.ts` validates `isMaxMode` on cached variants.
- `shared/cursor-model-selection-identities.mjs` owns canonical selectable model/context/fast identities and context-window key normalization shared by runtime discovery and the snapshot generator; its `.d.mts` file owns the TypeScript contract.
- `src/cursor-provider.ts` is a thin `streamCursor()` wrapper that delegates turn execution to the turn runner.
- `src/cursor-provider-turn-runner.ts` orchestrates provider turns (pre-send drain, prepare, send, finalize, emit, cleanup).
- `src/cursor-provider-turn-prepare.ts` owns turn prepare (auth, MCP timeout install, effective local HTTP transport configuration, session agent with the Cursor built-in tool allowlist, live-run setup, coordinator) and refuses omp advisor requests on the cloud runtime, where the SDK cannot restrict tools.
- `src/cursor-one-shot-request.ts` owns request routing (one-shot vs pooled agent, main conversation vs other omp agent loops such as advisors, recognized by their `advise` tool whether omp sends its tools natively or in-band under `PI_DIALECT`) and the Cursor built-in tool allowlist (`getCursorBuiltInToolAllowlist`: an omp advisor gets only the read-only `read`/`grep`/`glob` that omp granted, a compaction or branch summarizer gets none).
- `src/cursor-provider-turn-send.ts` owns SDK `agent.send()` wiring and abort listener registration.
- `src/cursor-provider-turn-finalize.ts` owns unified `awaitFinalizeCursorRunOutcome()` (wait, transcript replay, incomplete tools, artifacts, context cache).
- `src/cursor-sdk-billed-usage.ts` reads a finished cloud turn's billed row with `agent.getUsage({ runId })`, selected by the run id on the turn's own fresh agent. Local turns never call `getUsage()` and keep raw `turn-ended` usage. `src/cursor-usage-accounting.ts` copies a usable row (recorded, and `input + cacheRead + cacheWrite` within the model window, so omp's overflow classifier never sees billed spend above the window) into the spend buckets as additive counts and sets `usage.contextTokens` to the occupancy; a missing, failed, zero, or over-window row leaves the turn on approximate usage. `test/fixtures/cursor-sdk-billed-usage-1.0.34.json` separates captured rows from documented examples; it was captured on `@cursor/sdk` 1.0.34 and not re-captured for 1.0.40, whose usage declarations and mapper contract `test/cursor-sdk-billed-usage.test.ts` checks against the installed builds (the fixture's `contractVerifiedSdkVersions` lists both).
- `src/cursor-provider-turn-emit.ts` owns live vs direct emission from finalized outcomes.
- `src/cursor-provider-turn-types.ts` owns immutable turn phase data and explicit phase result types; phase-local cleanup stays inside the owning phase.
- `src/cursor-provider-run-outcome.ts` owns the discriminated `CursorRunOutcome` model and terminal emission classification.
- `src/cursor-provider-run-finalizer.ts` owns live-run wait completion, outcome application, debug finalization, and SDK abort-suppression disposal.
- `src/cursor-run-final-text.ts` owns final assistant text selection for run outcomes and live-run drain.
- `src/cursor-provider-errors.ts` owns scrubbed Cursor SDK run failure detail, abort reason formatting, and provider error sanitization. Connect errors are classified through a bounded, cycle-safe `cause` walk, so the SDK's `NetworkError` wrapper around an Unavailable/DeadlineExceeded/Internal `ConnectError` is classified from that cause; SDK provenance may come from any error in the chain (`test/cursor-sdk-network-error-wrapper.test.ts` pins the installed wrapper). An abort also reaches the host as the SDK's Unknown `ConnectError` around a canceled `ConnectError` around an `AbortError` (the bundled 1.0.34, 1.0.37 and 1.0.40 builds all raise it; no earlier build was checked); only that whole chain is classified as an abort, and the stall detector's wrapper, which has the same shape, is decided first as a retryable network failure by its `onStall` / `reportStall` frames. The same test file pins that chain in every build (`reportStall` calls `this.onStall?.()`, whose arrow cancels the request through `withCancel` synchronously) and runs the bundled detector; `test/cursor-sdk-retriable-stalled-contract.test.ts` pins the `RetriableError` `Connection stalled` premise behind `isCursorSdkConnectionStalledError`. Re-run both on every SDK upgrade.
- `src/cursor-provider-lazy.ts` owns the `streamSimple` wrapper that defers Cursor provider execution to invocation and converts provider runtime failures into stream errors; the provider module stays in Pi's static extension graph so host peers resolve through Pi's loader.
- `src/cursor-session-binding.ts` owns per-registration session bindings: omp re-runs the factory in the same module for every in-process subagent, so per-session state lives in binding slots (`cursorSessionSlot`), every handler, command and tool runs inside its registration's binding, and each provider call resolves its session from its provider state store or provider session id.
- `src/cursor-session-scope.ts` owns pi session cwd, session file/id/name/generation scope keys, and `session_start` / `session_info_changed` registration for session-agent pooling, cloud agent names, and debug grouping.
- `src/cursor-session-store.ts` owns per-session Cursor SDK SQLite store identity derivation, open/disposal, temporary fileless stores, and guarded removal. `admitRecordedCursorSessionStoreIdentity` is the only place a recorded store identity is admitted, for resume (`openCursorSessionStoreForScope`) and for cleanup (`src/cursor-session-agent-cleanup.ts`). Besides this session's current default and session stores it admits their exact MD5-derived counterparts, the layout `@cursor/sdk` used before 1.0.35 (`<project dir>/sdk-agent-store/md5(cwd)`, now `sha256(cwd)`, renamed by the SDK's first `getDefaultSdkStateRoot` call). A legacy identity maps onto the current root once the SDK has renamed the legacy root away, and is used as recorded while the legacy root still exists (never merged). The mapped store is not checked for existence: a gone store opens empty and the SDK reports the agent not found, which resume turns into a fresh agent (`createSessionAgentEntry`) and cleanup records as a retryable failure. Only ENOENT/ENOTDIR count as absent; any other filesystem error propagates. `test/cursor-session-store-legacy-root.test.ts` pins the installed SDK's rename and both hashes, so re-run it on every SDK upgrade.
- `src/cursor-http1.ts` owns branch-scoped local HTTP/1.1 session state, global-preference override tracking, and extension-owned SDK configuration/null reset.
- `src/cursor-ripgrep-path.ts` owns bundled Cursor SDK platform-package resolution shared by ripgrep and the native parsers (`resolveCursorSdkPlatformPackageDirectory`, including the on-disk `node_modules` fallback for runtimes that cannot resolve a bare specifier), local-agent environment initialization (`ensureCursorRipgrepPath` points `CURSOR_RIPGREP_PATH` at the bundled executable binary unless the variable is already an absolute path), and `ensureCursorTreeSitterVendorDir` (sets `CURSOR_TREE_SITTER_VENDOR_DIR` when it is unset, empty, or relative and both `vendor/tree-sitter*/index.js` entrypoints exist, because the SDK ignores non-absolute values and its own search only walks up from the omp binary; an absolute value is never changed, and a miss is remembered per process); `test/cursor-ripgrep-path.test.ts` and `test/cursor-tree-sitter-vendor-dir.test.ts` lock those against the installed SDK.
- `src/cursor-sdk-runtime.ts` owns the deferred Cursor SDK module loader. `loadCursorSdk` is the only runtime `@cursor/sdk` import, and before the SDK's first evaluation it takes the process-lifetime output filter lease (`installCursorSdkProcessOutputFilter`) and calls `ensureCursorTreeSitterVendorDir()`; `test/cursor-tree-sitter-vendor-dir.test.ts` locks both.
- `src/cursor-sdk-package-dir.ts` is a leaf module that owns `findCursorSdkPackageDir()`, the on-disk `@cursor/sdk` locator used by `src/cursor-ripgrep-path.ts`, because a Bun single-file compiled binary cannot resolve a bare specifier for a plugin file.
- `src/cursor-sdk-process-error-guard.ts` owns containment of Cursor SDK failures that escape as process-level errors: observed Cursor SDK failure shapes only (SDK stack provenance or Cursor backend `aiserver.*` error details, or the exact observed EPIPE shape during active provider turns), scoped to active provider turns or sessions. It has no spawn case: on `@cursor/sdk` 1.0.40 the spawn sites that were measured observe their spawn errors. The local shell returns its spawn error to the model through its exec replay cache, each of the three ripgrep spawns handles the child's `error` event (the test parses the bundled build and requires the listener inside the function around each spawn), and the ripwalk's `processExit` promise, which 1.0.34 left unhandled, gets its rejection handler where it is created (1.0.37 and later). `test/cursor-sdk-host-rejection-containment.test.ts` pins those SDK facts and keeps an end-to-end no-guard sentinel, a startup walk with a ripgrep that cannot start; if omp ever dies there, a ripgrep case has to come back. The same file pins the premises of the guard's EPIPE and closed-writable cases in every build: the only spawned-child stdin writes are the shell executor's two, git's one and the MCP transport's one, the only stdin `error` listener is the MCP transport's, the hook payload path swallows a closed pipe, and the controlled-exec stream drops `WriteIterableClosedError` and sends any other error to the model. Other spawn sites were not measured. With local sandboxing, a ripwalk whose call carries a workspace sandbox policy (the LS executor passes one) spawns the SDK's sandbox helper instead of ripgrep; that failure was not measured. Inside omp, rejections are contained through omp's `postmortem.interceptUnhandledRejections`, because Bun calls process error listeners directly (the `process.emit` patch never sees them) and omp's postmortem listener exits on unclaimed rejections. Uncaught exceptions stay fatal inside omp: its `uncaughtException` handler has no interceptor, and the guard does not apply postmortem's expected-cleanup marker, the exemption a plugin can use.
- `src/cursor-spawn-fd-guard.ts` wraps `Bun.spawn` and retains subprocesses whose stdio has an extra `"pipe"` or numeric fd. Bun 1.3.14's subprocess finalizer otherwise `close()`s those descriptors after the Cursor shell exits, and macOS kills omp with `EXC_GUARD` when SQLite has reused the number (guard `0x08fd4dbfade2dead`). The retain lasts for the process. Do not dispose those subprocesses.

- `src/cursor-max-mode.ts` owns Max Mode on a turn's model selection, and Max Mode is local-runtime only. `selectCursorMaxModeSelection` is the entry point (`src/cursor-provider-turn-prepare.ts`). A model without catalog variant information is never refused. `test/cursor-max-mode.test.ts` pins this, including that the SDK sets `maxMode` exactly where the plugin's rule says Max Mode only, against the installed bundled, esm and cjs builds, offline. No patch is needed for Max Mode.

## Operating rules

- Prefer the smallest change that preserves the current pi user contract.
- Treat Cursor SDK model metadata as the source of truth for model IDs, parameters, variants, thinking controls, and context variants. Do not hardcode new model-specific behavior unless it is a documented fallback.
- HARD REPO RULE: never guess what the Cursor SDK outputs, expects, or does. Always verify Cursor SDK behavior against the installed `@cursor/sdk` package and/or the official TypeScript SDK docs at `https://cursor.com/docs/sdk/typescript` before making claims or implementation changes.
- Contract-test external behavior before relying on it: when code depends on Cursor SDK/pi runtime payloads, timing, lifecycle, errors, usage accounting, or tool/event shapes, add or update a focused test that asserts the observed installed-package/docs/captured-fixture contract and fails if that contract drifts. Do not replace this with mocks based on guesses.
- CODE IS TRUTH: claims about behavior must be backed by current source code, installed dependency code/types, contract tests, or captured command output. If evidence is missing, say `unknown`; do not infer, soften, or fill gaps with assumptions.
- Before every commit and before every push, run a thermo-nuclear/deep maintainability review on the exact diff being committed or pushed. Remediate every material finding and repeat the review until there are no remaining material findings. Do not commit or push without this review evidence.
- Keep pi-native abstractions first: context is a model variant, thinking uses pi thinking metadata, and Cursor-only `fast` and Max Mode are extension state/status.
- Preserve the default pi footer; use extension status only for Cursor-only state such as `cursor:local · fast:on`, `cursor:local · fast:off`, `cursor:local · fast:on · max:on`, and `cursor:cloud · fast:n/a`. Max Mode applies to the local runtime only: it defaults on when no override is set and is sent as `ModelSelection.maxMode`. No patch is needed for it, Cursor Cloud never carries it, and `max:on` is never shown for cloud. With it off, a variant the catalog lists as Max Mode only is refused before sending, because the SDK would run it in Max Mode anyway. The optional `npm run patch:cursor-sdk` turns off the local agent's default `Co-authored-by: Cursor <cursoragent@cursor.com>` trailer; re-apply it and restart omp after install. Cloud agents still add the trailer.
- Stop discovery once package scripts, README, config files, tests, and the relevant `src/` modules explain the task. Do not broad-search `node_modules` unless debugging a dependency API.
- Ask the user before changing public UX, published package metadata, dependency families, or behavior that requires a migration. Otherwise proceed and verify locally.

## Security and side effects

- NEVER store Cursor API keys in repo files, `~/.pi/agent/cursor-sdk.json`, tests, logs, snapshots, or docs examples.
- Scrub Cursor SDK errors and output that may contain API keys, bearer tokens, cookies, sessions, or auth headers.
- `PI_CURSOR_SDK_EVENT_DEBUG=1` and `npm run debug:provider-events` write raw local artifacts that may include prompts, tool args/results, local paths, or secrets; keep them under gitignored `.debug/`, do not print or commit them, and keep run-scoped debug state explicit rather than process-global.
- Ambient Cursor settings/rules loading is enabled by default through `PI_CURSOR_SETTING_SOURCES=all`; keep the exact-frame SDK output filter intact so settings/skills output does not corrupt pi's TUI. Users can narrow or disable Cursor setting sources explicitly when desired.
- Live omp/Cursor smoke tests may call external services and require `CURSOR_API_KEY` from `~/.omp/.env` (loaded at omp startup) or the environment; provider turns also accept omp's resolved `options.apiKey`. Run them for Cursor provider/runtime changes. If auth is unavailable, report live smoke as release-blocked instead of skipped-ready. See `docs/cursor-testing-lessons.md` for `CURSOR_API_KEY` in isolated runs.
- Every live `omp` run (print, RPC, `models`) passes `--config <overlay>` with memory off: omp's memory backend is the maintainer's shared Hindsight bank, where `hindsight.mentalModelAutoSeed` creates two mental models for every new working directory and auto-retain may store turns. Overlay: `memory: {backend: off}`, `hindsight: {mentalModelAutoSeed: false, autoRetain: false, autoRecall: false}`, `autolearn: {enabled: false}`, `advisor: {enabled: false}`.
- For live runtime evidence, use `cursor-sdk/composer-2-5@slow` as much as needed. If Cursor Cloud does not support that exact model variant, use `cursor-sdk/composer-2-5`.
- Live Cursor Cloud probes that create `bc-*` agents must capture agent/run IDs, verify archive/delete cleanup, and report any residual agent; do not assume cleanup from a passed smoke.
- For Cursor provider/runtime changes, the gate is the omp-native pre-commit validation below. The Pi-era smoke scripts are unported (see `## Setup and commands`) and are not a gate.

## Cursor Cloud specific instructions

This is an omp provider extension (not a server/web app). "Running the app" means launching `omp` with this extension loaded. Standard commands live in `## Setup and commands`; only the non-obvious caveats are below.

- Dependencies install with `npm install`. There is no build step; omp loads `./src/index.ts` directly under Bun.
- Node: `engines` requires `>=22.19.0`. Prefer a compliant Node on `PATH` for tests and live `omp` (for example `nvm use 22.22.2`). Older Node may run some commands but is unsupported.
- `CURSOR_API_KEY` is provided as a cloud-agent secret, so live Cursor runs and full live model discovery work without a Pi `/login` flow. `npm test`, `npm run typecheck`, and `npm pack --dry-run` need no key.
- Run the extension locally with `./node_modules/.bin/omp -e ./src/index.ts --model cursor-sdk/composer-2-5` (`@oh-my-pi/pi-coding-agent` 18.3.4 installs that binary). Print-mode smoke: `./node_modules/.bin/omp -e ./src/index.ts --model cursor-sdk/composer-2-5 --cursor-no-fast --no-session -p "..."`.
- Cold-start gotcha: the *first* Cursor SDK run in a fresh VM can take several minutes (SDK/transport warm-up); subsequent runs complete in ~10s. Warm up with one throwaway run before any timing-sensitive or recorded demo, and don't treat a slow first run as a hang.
- When capturing print-mode (`-p`) output, redirect stdout to a file rather than piping through `tail`/`head` — those pipes buffer until the process exits, hiding streaming progress.
- Use sessionful runs (`--session-dir`, then `--continue`/`--resume`; not `--no-session`) when testing session ledgers, resume identity, branch/fork/clone/switch behavior, or slash commands such as `/cursor-cloud`; `--no-session` is only proof for one-shot provider behavior.
- For slow cloud or slash-command probes, prefer print mode for model turns or raw JSONL RPC with an explicit timeout; the packaged `RpcClient` has a fixed 30s request timeout that can falsely fail long cloud operations.
- Basic setup validation here is the pre-commit validation above: unit tests, typecheck, `omp models cursor-sdk -e .`, and print/RPC turns. The Pi-era smoke scripts (`smoke:visual`, `smoke:live`, `smoke:platform*`, …) are unported and need the Pi CLI; see `## Setup and commands`.
